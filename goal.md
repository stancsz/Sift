# Goal: LongBench v2 with OpenRouter MiniMax M3

## Objective

Produce a reproducible, provider-attributed comparison of Sift and full-context prompting on a frozen 100-task LongBench v2 sample, using OpenRouter's MiniMax M3 route. Report answer quality, actual input-token reduction, latency, and cost from the same paired requests. Use the results to decide what performance and savings claims are supported.

## Chosen model route

- Model: `minimax/minimax-m3` through OpenRouter (`openrouter/minimax/minimax-m3` in the Subroute LiteLLM configuration).
- Do not use the `auto` alias or a route that can switch to direct MiniMax, Xiaomi, or Codex. Isolate this evaluation route from LiteLLM and OpenRouter model fallbacks, and record the provider and model returned for every generation. If OpenRouter changes the provider, mark the sample as a routing deviation and do not silently count it as MiniMax.
- Keep credentials in the existing environment configuration. Never put API keys in this repository or benchmark output.
- OpenRouter's model page lists a 1M-token model context, but the selected MiniMax endpoint metadata checked 2026-10-16 reports a 524,288-token prompt limit, 512,000-token completion limit, and prices of $0.30/M input and $1.20/M output. The frozen manifest records this provider-specific metadata. Recheck it immediately before the primary run.

## OpenRouter MiniMax execution plan

Use OpenRouter as the single, observable API entry point for the primary MiniMax LongBench v2 comparison. Pin the request to `minimax/minimax-m3`, require OpenRouter's MiniMax provider, disable provider fallbacks, and verify the returned provider/model for every response. This keeps the paired arms on the same model route and makes routing deviations visible in the raw record.

1. **Freeze a fair, reproducible sample.** Select 100 distinct LongBench v2 cases from the pinned public training data. Render them with the pinned MiniMax M3 tokenizer and chat template. Every selected full-context prompt exceeds the configurable 32,768-token Sift target. The frozen 150K cap yields 225 eligible cases and a balanced 100-case sample with domain, difficulty, dataset length-label, and M3 token-size strata. No eligible candidate has the dataset's `long` length label; disclose this and do not imply full-suite or blind-holdout coverage. The selected maximum is 145,686 local tokens.
2. **Check the protocol before spending.** Freeze case IDs, answer keys, prompt hashes, tokenizer/template hashes, sampling seed, Sift core hash, runner hash, and the exact composition. Confirm 100 unique cases, all token thresholds, balanced strata, and context projections below the observed 524,288-token request limit. Recheck OpenRouter's live price and calculate both expected cost and maximum request-size projection.
3. **Smoke-test the route.** Run one frozen case, one repeat, and both arms with one worker. Confirm provider/model attribution, no fallback, identical task semantics, valid structured-choice handling, provider usage/cost receipts, prompt-token reconciliation, latency capture, and correct spend-guard accounting. Preserve failures and raw responses; do not retry or replace cases silently.
4. **Run the paired evaluation.** If protocol and spend gates pass, run 100 cases × 3 paired repeats × 2 arms (600 generations). Randomize arm order within each pair and keep the same seed/settings for each paired comparison. The arms are full original context and Sift at the 32,768-token target. Save every request, response, error, usage receipt, timestamp, and result so the analysis can be regenerated.
5. **Report performance and savings together.** Report per-arm accuracy, per-repeat and per-case majority results, paired wins/losses, invalid outputs, actual provider-reported input-token reduction, upstream-reported cost reduction, and latency. Keep input-token savings separate from total cost savings, and identify any BYOK upstream cost as provider-reported rather than an invoice. Publish only measured claims with the sample size, date, route, aggregation method, and limitations beside them.
6. **Use the result to improve Sift, then repeat.** Diagnose errors by task and failure type, make a targeted algorithm change against independently reviewed cases, and rerun the same frozen manifest and protocol. Preserve the original run and code hash so the before/after comparison remains auditable. Update README claims only after that comparison supports them.

The runner uses a conservative 4× local-input cost reserve and a separate 3.25× request-size projection. Both are best-effort client-side safeguards, not hard OpenRouter billing/context limits. At the verified MiniMax endpoint rates, the current 4× preflight for 600 calls is $40.902732, above the working $20 ceiling. The one-case paired smoke is next; if each arm's provider prompt count is within 1.1× of the frozen local count, reduce the reserve to 1.5× for the primary run, giving a projected $15.35. Otherwise keep 4× and do not start all 600 calls under the current ceiling.

## Frozen comparison design

- Dataset: LongBench v2 pinned to the dataset revision and data hash recorded in the new M3 manifest. The Qwen manifest is a separate experiment and is not the source of the M3 sample definition.
- Sample: use the frozen 100-case manifest at `docs/evals/longbench-v2-minimax-m3-100-manifest-2026-10-16.json`. All cases are >32,768 and <=150,000 local M3-rendered prompt tokens. The selected set has 44 short /56 medium /0 long labels, easy/hard=50/50, token bands=38/30/32, and 50.8K projected headroom at the largest selected prompt. It is a length-conditioned development sample, not a full-suite score or blind holdout. IDs, prompt hashes, answer keys, seed, tokenizer/template, Sift core, runner, and preparer hashes are frozen.
- Arms: (1) full original context; (2) Sift-compressed context. Keep the final question and message roles identical.
- Repeats: three paired repeats per case and arm (600 generations total), with randomized arm order within each pair. Preserve raw generation records and per-task outcomes.
- Task score: valid structured-choice answer and exact match to the published answer key. Report per-repeat results, per-case majority results, and paired disagreements; do not use only the best repeat.
- Record request/response timestamps, provider-reported prompt and completion usage, returned provider/model IDs, HTTP status, finish reason, schema validity, answer, correctness, and estimated/model-reported cost for each call.

## Token-budget and cost accounting

The earlier Qwen sample used Qwen tokenization and a 24,576-token target. For the primary MiniMax evaluation, use the configurable 32,768-token default and count rendered prompts with the pinned MiniMax tokenizer and chat template. Record tokenizer/template hashes, target, 150K maximum, and safety margin in the frozen manifest. Verify all 100 selected full prompts exceed the target and fit the conservative route limit; use identity/passthrough outcomes as explicit failures of that invariant rather than silently omitting them.

Use OpenRouter's returned prompt usage and `cost_details` as the source for provider-reported cost and input-token savings. The existing OpenRouter screens used BYOK and reported `cost: 0`, `is_byok: true`, and nonzero upstream inference costs; label those values as upstream-reported pass-through costs, not verified invoices. Calculate cost savings as `(full-context upstream cost - Sift upstream cost) / full-context upstream cost`; calculate input-token reduction separately using actual provider-reported prompt tokens. Include output and any billed reasoning usage in total cost.

Recalculate expected spend from the frozen M3-tokenized prompts and verified MiniMax endpoint rates immediately before the run. The current 4x local-token reserve estimates $40.902732 for the paired 600-call run, which fails the $20 working ceiling. Prior M3 development receipts matched local/provider prompt counts 47/47 times; after the longest-case paired smoke, use a 1.5x reserve only if both observed ratios are <=1.1, otherwise keep 4x. Separately project request size at 3.25x local tokens plus the 16-token output cap against the verified 524,288-token endpoint prompt limit. These are best-effort client-side guards, not hard provider-enforced billing/context limits. The runner tracks provider-reported costs and stops dispatching when receipts plus in-flight estimates reach the budget, but already dispatched requests may still bill.

## Execution stages and gates

1. **Finish and preserve the current Qwen run.** Do not restart or modify its service mid-run. Label its existing cache behavior accurately and do not present it as a cache-clean confirmation.
2. **Harden the existing MiniMax runner.** Reuse `benchmarks/run_longbench_v2_minimax.py`; do not create a duplicate or point the Qwen runner at OpenRouter unchanged. Lock the OpenRouter model/provider route with provider fallbacks disabled, verify the returned model and provider per call, retain complete response/error and usage evidence, support three randomized paired repeats at the single 32K target, and implement a local conservative spend ceiling.
3. **Freeze a new 100-case M3-tokenizer manifest.** Use only local pinned LongBench data, tokenizer, and chat template; require every selected full prompt to exceed 32,768 tokens and fit the full-context window. Balance length, domain, and difficulty where candidate counts allow; publish the selection policy and actual composition.
4. **Run a paired smoke test** on one frozen case, one repeat, both arms. Verify OpenRouter model/provider attribution, no provider/model fallback, structured choice, equal task prompt semantics, usage and cost fields, latency capture, and budget accounting. Reconcile OpenRouter-reported prompt tokens against the tokenizer/template estimate.
5. **Run the frozen 100-case evaluation** only after the smoke-test and spend gates pass. Use the pinned sample and fixed settings, preserve every attempt and failure in raw results, and never silently replace invalid calls.
6. **Audit, report, and update the README.** Summarize sample selection, provider route, model/version, dataset revision, Sift version and exact tokenizer/target definition, repeat aggregation, task accuracy, paired changes, provider-reported input reduction and upstream cost savings, preprocessing time, model latency, and confidence limits. Separate LongBench QA evidence from native Codex/Claude Code agent-workflow evidence. Do not imply LongBench alone proves end-to-end coding-agent quality or generalizes to the full suite.

## Completion criteria

- Every counted response is attributable to OpenRouter MiniMax M3, with no unreported fallback.
- Raw inputs, outputs, usage, timing, per-task scores, and price assumptions are saved in a reproducible result artifact with secrets excluded.
- The README presents results and savings only as measured, with sample size, run date, protocol, and known limitations adjacent to the claims.
- The benchmark scripts and documentation are committed and pushed after the result is reviewed.
