# LongBench v2 MiniMax paired study specification

## Purpose and interpretation

This is a descriptive, paired outcome study of **current default Sift versus full context** on the 344-task conservative, historically route-screened cohort. It measures whether the current Sift default changes exact-choice answer quality, task-majority accuracy, prompt usage, observed provider cost, request latency, and preprocessing time on eligible tasks.

It is not a blind holdout, a test of a new selector, a full 503-task result, or a multi-turn agent-completion benchmark. The public 503-row prompt/label census exposed every task ID, and earlier candidate work has failed its current offline gate. Experimental selectors remain default-off and are excluded. Any result must be described as post-census development evidence for this historically screened cohort; it cannot establish generalization, quality preservation, a causal candidate lift, or Codex/Claude Code completion-time savings.

The study is still worth completing as a larger matched measurement of the released/default behavior: both arms are regenerated from the same frozen task rows, use the current pinned Sift core and exact MiniMax renderer, run concurrently under one protocol, and are scored with a predeclared paired analysis. At 344 tasks, it exceeds the user's requested 100-task minimum while using the conservative historical fit screen. The existing 100-task results are cross-run development evidence, not a substitute for this paired run. The existing candidate-selected 14-task replay is exploratory and must not be pooled into the study.

## Arms, requests, and route gate

- **Full:** the complete benchmark context, question, and choices rendered by the pinned MiniMax template.
- **Default Sift:** the same task through the current default Sift implementation at a configured target of 32,768 tokens and 128-token safety margin (effective target 32,640). No experimental selector or manual repair is allowed.
- Use three zero-based repeats (`0`, `1`, `2`) per task per arm: 344 × 2 × 3 = **2,064 requests**. Randomize and interleave arm/repeat order within task blocks using a frozen seed. Preserve exact request-body hashes and the schedule before dispatch.
- Freeze exact request generation in the manifest: temperature `0.1`, top-p `0.8`, reasoning disabled, streaming with usage receipts, and paired generation seed `study_seed + repeat + 1`. Treat the seed as a matched request parameter, not a guarantee of deterministic sampling; verify the provider accepts the specified settings in the dispatch gate. Set `max_tokens=64` for both arms; the prior 16-token cap produced four truncated Full responses in the 100-task evidence. Use the pinned prompt builder's exact instruction: system asks to answer from supplied context and return exactly one of `A`, `B`, `C`, or `D`; final question suffix is `Return only the letter A, B, C, or D.` Only trimmed outputs exactly equal to a single capital letter A–D are scorable. Hash the prompt builder, template renderer, literal request body, scoring code, and generated schedule.
- Pin requested model `minimax/minimax-m3` to provider `minimax`, disable fallback, and record the resolved endpoint model. Immediately before dispatch, refresh endpoint ID, prompt/completion limits, prices, account usage, unsettled requests, and total reserve.
- The listed endpoint prompt ceiling is 524,288. Historical pinned receipts verify local/provider prompt-token equality only through 150,000. Every Full prompt in the 344-task cohort is at or below that boundary; still verify the current pinned route and usage receipt on the first request before continuing. If that receipt mismatches, stop, preserve it, and do not silently shrink/substitute the cohort. Do not treat one request as route verification for the 111-task extension pool.
- After route verification, stop on provider/model drift, fallback, prompt-token mismatch, missing usage/cost data, context rejection, Sift failure, or spend guard. No retries, replacements, answer repair, or unplanned model-setting changes. Incomplete or invalid output scores incorrect.

The dated reserve is **$41.86563525** for three repeats under $0.30/M input, $1.20/M output, 1.5× uncached-input reserve, and the specified 64-token output cap. This updates the earlier 16-token estimate by including 48 additional output tokens for each of the 2,064 requests. It is a modeled estimate, not a quote or current liability; the live route and reserve must be recomputed from the concrete frozen requests. A $50 cap is a suggested contingency, not user authorization. Do not dispatch any paid request without fresh explicit authorization for a sufficient aggregate cap and a refreshed account/in-flight ledger.

## Outcomes and analysis

**Primary outcome:** per-task majority correctness (correct if at least two of three strict A–D responses equal the pinned key). Report Full and Sift task counts, the paired Sift-minus-Full percentage-point difference, discordant task counts, and a paired task-cluster bootstrap 95% interval with a frozen seed and at least 20,000 resamples. Include the exact scoring implementation hash.

**Secondary outcomes:** per-response exact accuracy (1,032 responses per arm), paired per-repeat correctness, invalid/incomplete output counts, prompt/completion/cache-read/cache-write tokens, provider-reported pass-through cost, uncached-price reconstruction, preprocessing duration, model latency, and full elapsed runtime. Report all 344 tasks by domain/difficulty/length and distinguish missing/invalid outputs from excluded tasks. Use provider receipts as the source for realized cost and token usage; keep local projections separately labeled.

Make no quality or statistical-significance claim solely from direction of the point estimate. State sample size, exposure, route, cache treatment, uncertainty interval, and comparison scope next to all figures. A LongBench result cannot be presented as a multi-turn agent completion-time measurement.

## Gates and publication

1. **Offline gate:** independently reproduce the 344-task eligibility map and 2,064-job manifest; verify all frozen hashes, exact generation/answer-format settings, provider-specific cost math, request limits, and that prepare-only mode has no network/API path. Keep the 455-task local-fit extension list separate and label its route status unresolved.
2. **Funding/route gate:** refresh route/account/in-flight facts and obtain explicit sufficient spend authorization. The prior `$20` aggregate / `$4` run guard is exhausted and does not apply.
3. **Dispatch gate:** independently review exact request construction, stop conditions, output scoring, accepted request settings (including seed behavior), and the route-verification sequence before any request.
4. **Result gate:** preserve raw response/usage receipts; independently reproduce scoring, paired uncertainty, usage, cost, and timing before reporting.
5. **Product gate:** make no README, Awesome README, or production quality/savings change based on this specification, the modeled fit audit, or the 14-task retrospective. Update marketing only after result review, with the limitations above visible next to claims. Do not change Sift defaults from benchmark direction alone; require a separately justified implementation and evidence-retention review.
